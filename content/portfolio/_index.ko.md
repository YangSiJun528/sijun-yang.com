### 병목 성능 진단 체계 구축



#### 문제

운영 API에서 장애나 지연이 발생하면 애플리케이션 로그를 건별로 검색해 원인을 추적해야 했습니다.<br>여러 요청의 로그가 섞여 하나의 요청 흐름을 따라가기 어려웠고, 어떤 API와 사용자 구간에서 지연이 반복되는지 정량적으로 비교하기도 어려웠습니다.

#### 해결

서비스 규모 대비 도입·운영 비용을 고려해 기존 환경에 적용할 수 있는 MDC와 AWS Athena를 도입했습니다.

각 요청에 `requestId`를 부여하고 MDC에 저장해, 하나의 요청에서 발생한 로그를 함께 추적할 수 있도록 했습니다.

ALB access log는 S3에 적재하고 Athena external table로 조회하도록 구성했습니다.<br>API 엔드포인트, 기간별 메트릭, p50/p95/p99 처리 시간과 에러율 등을 비교하는 쿼리를 정리해 팀에 공유했습니다.

#### 성과

`느린 API 선별 → 요청 단위 원인 추적 → 코드 변경 → 동일 지표 재측정(개선 수치 측정)`순서의 진단 절차를 구축했습니다.

이를 적용해 다음과 같은 개선을 달성했습니다.

- 채널 글쓰기 3,150ms → 42ms: 동기 FCM 호출을 비동기로 전환
- 뉴스피드 렌더링 2,150ms → 133ms: 게시물별 댓글 조회를 일괄 조회로 변경
- 친구 추천 쿼리 3,020ms → 61ms: `OR` 조인을 분리하고 `UNION ALL`을 적용

### Instagram 업로드 자동화 어드민 기능 개선

#### 배경

운영자는 관리자 화면에서 접수된 자기소개 신청을 확인하고, 학교별 Instagram 계정에 게시물과 스토리를 업로드했습니다.

<div class="portfolio-step portfolio-step--flow">
<div class="portfolio-step-copy">

#### 문제 상황

기존에는 Instagram API로 스토리/게시물을 업로드하고 내부 상태를 갱신하는 작업이 하나의 요청 안에서 실행되고 있었습니다.

- 외부 업로드가 일부 완료된 뒤 중단되면 DB에는 상태가 갱신되지 않아, Instagram의 실제 상태와 서버 상태의 불일치가 발생합니다. (계정 또는 Instagram API의 일시적 문제로 업로드가 수십 회에 한 번씩 실패하곤 합니다.)
- 운영자는 최종 성공,실패만 확인할 수 있어, 원인 파악과 복구를 위해 매번 개발자에게 요청해야 했습니다.

#### 분석

작업 실행과 상태 관리가 요청의 수명에 묶여 있는 구조가 문제라고 판단했습니다.

이 문제를 해결하기 위한 요구사항을 정의했습니다.

- 여러 업로드 작업을 순서대로 연결하고 단계별 진행 상태를 확인할 수 있어야 함
- 실패 단계와 원인을 기록하고, 자동 재시도와 운영자의 수동 재개를 지원해야 함
- 소규모 팀이 쉽게 도입하고 유지할 수 있어야 함

트래픽이 적은 내부 기능이므로 별도 메시지 브로커를 운영하는 대신, 기존 DB를 활용하는 [db-scheduler](https://github.com/kagkarlsson/db-scheduler)를 선택했습니다.

추가되는 DB 테이블이 적고, Spring 환경을 지원한다는 점 등을 고려하여 채택하였습니다. 데모 환경에서의 테스트로 예상 트래픽을 처리할 수 있음을 확인하였습니다.

#### 2. 제품 데이터와 채팅 데이터 통합

채팅과 다른 기능의 연계가 늘어, 두 저장소에 걸친 변경의 정합성을 관리하기 어려워졌습니다.

채팅 기능을 내재화하고 데이터를 마이그레이션하여, 채팅 로직과 실시간 이벤트 전달을 담당하면 채팅 서버를 구현하였습니다.

기존 Spring 환경에서 도입 복잡도를 줄이고, 당시 필요한 서버→클라이언트 이벤트 전달을 구현하기 위해 SSE를 선택했습니다. 채팅과 제품 데이터를 같은 저장소에서 관리하고, 서버에서 채팅 처리와 이벤트 전달을 제어할 수 있게 됐습니다.

#### 3. 비즈니스 로직과 실시간 연결 관리 분리

데이터 통합 후 수개월이 지나, 실시간 기능이 채널/게시글까지 확대되면서 연결과 구독을 별도로 관리할 필요가 커졌습니다. 당시에는 채팅 로직과 실시간 처리가 한 서버에 묶여있어, 다음과 같은 문제가 발생했습니다.

- 채팅 로직을 수정해 배포할 때도 SSE 연결이 종료됩니다.
- 기존 로직에 실시간 기능을 추가하려면 해당 로직의 실행 환경을 채팅 서버로 이전해야 했습니다.

문제를 해결하기 위해, 실시간 처리를 위한 Live 서버를 만들고, 채팅 로직과 DB 처리는 기존 API 서버로 옮겼습니다.  Live Server는 DB 의존성을 제거하고 WebSocket 연결과 채널 구독을 관리하도록 변경했습니다. 기존 API 서버에서 Redis Pub/Sub으로 이벤트를 발행하면 Live 서버가 구독 중인 클라이언트에 전달하도록 구성했습니다.

#### 한계

Redis Pub/Sub은 이벤트를 보존하지 않아 이벤트가 유실될 수 있습니다.

이는 비용과 운영 복잡도를 고려해 감수한 한계입니다. 실제 상태는 DB에 영속적으로 저장되므로 실시간 이벤트는 상태 변경을 알리는 용도로만 사용하고, 필요한 현재 상태는 HTTP API를 통해 다시 조회할 수 있도록 설계했습니다.

이러한 한계와 보완 방식을 인수인계 문서에 명시해 공유했습니다.
